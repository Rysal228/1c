# Хранение парольных хешей веб-приложения в 1С 8.5.1

**Статус:** хранение хешей проверено вручную в 1С 8.5.1.1522; **парольный вход Django не переключён**. В этом изменении нет нового HTTP-эндпоинта установки или проверки. Подготовка защищённого входа — отдельная задача.

## Выбранная архитектура

- Единственный источник бизнес-учётных записей — справочник `ПользователиПриложения` и его штатный UUID ссылки.
- Парольные хеши веб-аккаунтов хранятся **только в 1С** в отдельном непериодическом регистре `ПаролиПользователейПриложения`: измерение `Пользователь` (СправочникСсылка.ПользователиПриложения), ресурс `СохраняемоеЗначение` (строка 1024), один набор на пользователя.
- Форма публичного профиля и список специалистов хеш не возвращают. Полнотекстовый поиск и история изменения значения хеша отключены; стандартные команды регистра отключены. **Перед реальным использованием обеспечить ограничение доступа к регистру.** Сейчас список системных пользователей ИБ пуст, а значит, полноценные разграниченные права оператора не настроены. Скрытие в UI не является ограничением доступа.
- Для вычисления/проверки используем методы платформы `ВычислитьСохраняемоеЗначениеПароляПользователя` и `ПроверитьСоответствиеПароляПользователяСохраняемомуЗначению`. Реальный пользовательский smoke-тест на 1С 8.5.1.1522 подтвердил обе операции (успешное совпадение и отказ неправильного пароля). Это не заменяет тесты будущего сетевого входа.
- Сначала в параметрах информационной базы настроить **PBKDF2-HMAC-SHA256**. При неизвестном алгоритме или SHA-1 пароли не создавать: выбор алгоритма для пользователей ИБ может влиять на используемое глобальными методами значение.
- Django пока продолжает выдавать JWT по старому механизму; MAX, регистрация, автомобили, чаты и заказы не меняются.

## В дереве конфигурации

1. После бэкапа открыть Конфигуратор.
2. Создать информационный регистр `ПаролиПользователейПриложения`, непериодический, независимый, с ключом/измерением `Пользователь: СправочникСсылка.ПользователиПриложения` и единственным ресурсом `СохраняемоеЗначение: Строка(1024)`. Можно взять XML-файл `InformationRegisters/ПаролиПользователейПриложения.xml` и загрузить его в конфигурацию, если используемый способ загрузки сохраняет UUID метаданных. Проверить названия и состав.
3. Выключить стандартные команды регистра, полномасштабный текстовый поиск и историю хеша; настроить запрет чтения регистра обычными ролями. Проверить, что доступ к нему не открыт через внешние интерфейсы 1С.
4. В HTTP-модуле `ServiceCarAPI` находятся **только внутренние** процедуры `ВычислитьХешПароляПриложения`, `УстановитьПарольПриложения`, `ПроверитьПарольПриложения`. **HTTP-обработчиков для вызова этих процедур пока нет.** Если импортируешь модуль, предварительно сравни его с актуальным живым модулем и проверь синтаксис 1С.
5. Синтакс-помощником (при необходимости) проверить сигнатуру вызовов `ВычислитьСохраняемоеЗначениеПароляПользователя`, `ПроверитьСоответствиеПароляПользователяСохраняемомуЗначению` и тип возвращаемого значения; если потребуется исправление сигнатур, сперва внести его в GitHub.
6. Проверка уже пройдена вручную: строка хеша 224 символа сохранилась и прочиталась полностью (224/224), корректный пароль принят; временная транзакция отменена. **Не создавать новые реальные пароли через произвольную внешнюю обработку до контроля доступа оператора и плана смены входа Django.** Описание формы для доверенного локального оператора: `docs/initial-password-setup-local-1c.md`.

## Защита соединения Django ↔ 1С

Текущая публикация `http://host.docker.internal:8081/ServiceCar/hs/api` допускает анонимные внутренние запросы через `ONEC_ALLOW_UNAUTHENTICATED_INTERNAL=1`. **Её нельзя просто использовать для POST пароля.**

Следующая техническая задача — безопасный auth HTTP-маршрут, доступный только backend по **TLS** с проверкой сертификата и с 1С техническим пользователем/Basic или иным проверенным service credential. Необязательно заводить отдельную БД или публикацию, но нужно исключить обход защиты через прежний HTTP :8081. Не размещать технический пароль в GitHub. Не использовать `verify=False`, а также запретить журналирование тела password-запросов в Django, 1С и reverse proxy.

Будущие операции (не реализованы в текущем PR):
- `POST /auth/password/verify` → телефон/пароль, ответ лишь `authenticated`, `onecId`, актуальные роли и статус;
- `POST /auth/password/set` → разрешено только после доказанной идентификации пользователя либо через админский защищённый reset, **никогда** по одному `onecId` из публичного запроса;
- регистрация в 1С должна создавать пользователя и пароль в одной транзакции;
- для смены пароля обязателен текущий пароль или отдельно одобренный безопасный reset.

Не включать вход для реальных пользователей до реализации ограничений по частоте/блокировок и проверки прав на каждый метод.

## Миграция трёх аккаунтов

Только после завершения защищённого механизма — организовать подтверждённую смену паролей для трёх текущих пользователей. **Не просить пересылать пароль в чат, не вставлять его в командную строку или GitHub.** Для MAX-only учётной записи пароль не обязателен.

## Последующий переход

Сначала smoke test только тестовой учётной записи через защищённый вход. Затем регистрация, парольный вход Django, проверка ролей, refresh и совместимость JWT. В существующей базе есть внешние ключи автомобилей, заказов и чатов на `CustomUser`; пока они не заменены, не менять в публичных JWT значение `user_id` и не удалять `CustomUser`.

Логика MAX **полностью вне этого PR** и будет обсуждаться отдельно до её изменения.
