# Синхронизация времени записи: HTTP API и документы 1С

## Почему ручная запись 09:40 не появлялась на сайте

Ранее `OrderAvailabilityGet` читал `РегистрСведений.ЗанятыеИнтервалы`.
Запись через `OrdersPost` явно формировала бронь, а обычная форма
документа `ЗаказыНаОбслуживание` — нет. Исторический документ на
09:40 физически есть, но запись в регистре могла отсутствовать.

## Как работает после изменений

- Модуль **объекта** документа `ЗаказыНаОбслуживание` обрабатывает
  `ПередЗаписью` и `ПриЗаписи` и занимается блокировкой, проверкой
  времени и обновлением независимого регистра `ЗанятыеИнтервалы`.
  Эти события срабатывают и при HTTP `Объект.Записать()`, и при
  интерактивном сохранении в 1С.
- При изменении даты/времени старое бронирование снимается, новое
  записывается в той же транзакции. Изменение иных полей не трогает
  бронь. Пометка на удаление и физическое удаление освобождают слот.
- HTTP `OrdersPost` и `OrderByIdPatch` больше **не вызывают**
  отдельную запись/перезапись брони: иначе было бы два интервала
  на один заказ.
- `OrderAvailabilityGet` дополняет регистр датами самих документов,
  чтобы старые ручные заказы без регистровой записи тоже показывались
  занятыми. Дубликаты интервала `начало-конец` для JSON исключаются.
  `ЗаказПроверитьСлот` также учитывает эти документы и не разрешает
  клиенту занять старый ручной интервал.
- Внутри документа применяются те же основные правила:
  будущая дата, рабочий день, шаг, длительность, блокировки и
  отсутствие пересечения с записями сайта и других документов.

## Пример: 22.10.2026, настройки 60 минут / шаг 30 минут

Уже существующий документ 09:40–10:40 будет учтён в `busySlots`,
даже если его нет в регистре. Он делает недоступными запуски
09:00, 09:30, 10:00 и 10:30, поскольку интервалы пересекаются.
Согласно новым правилам *новый* документ на 09:40 через форму
сохранить нельзя: начало должно соответствовать шагу 30 минут.
Если ранее существуют сразу заказы 09:00–10:00 и 09:40–10:40,
это исторический конфликт — система его не «исправит» автоматически.
Менеджеру следует проверить и согласовать время с клиентами.

## Порядок установки

1. Сделать резервные копии ИБ 1С и выгрузки конфигурации.
2. **Перед этой правкой** убедиться, что применена [правка даты документа
   #24](https://github.com/Rysal228/1c/pull/24):
   `Объект.Дата = ТекущаяДата();` после `СоздатьДокумент()` в
   `OrdersPost`. На момент подготовки PR #24 не был слит.
3. Перенести оба изменённых модуля **вместе**:
   - `HTTPServices/ServiceCarAPI/Ext/Module.bsl`
   - `Documents/ЗаказыНаОбслуживание/Ext/ObjectModule.bsl`
   Не обновлять только один: иначе новые брони не сформируются
   или будут дублироваться.
4. Проверить конфигурацию (F7), обновить конфигурацию БД,
   перезапустить публикацию HTTP при необходимости.
5. Проверить в тестовой ИБ, а затем на рабочей:
   - новый заказ через сайт: документ + **одна** бронь, HTTP 201;
   - запись через стандартную форму на свободное 13:00:
     документ + бронь; 13:00/13:30 не доступны в календаре;
   - ручная 13:40 отклоняется при шаге 30 минут;
   - ручная 13:30 отклоняется после записи на 13:00 (60 мин);
   - изменение времени ручного заказа: старая бронь удаляется,
     новая появляется; удаление/пометка освобождает;
   - старый документ 09:40 из Предприятия отображается занятым
     в `busySlots` даже без регистровой записи;
   - фронт не предлагает ни одного слота, пересекающегося с 09:40.

## Ограничения

- Исторические документы, созданные **до** этой правки, не
  перенумеровываются и не изменяются автоматически; для их
  отображения выполняется дополнительное чтение документов.
- При большом числе заказов за день запрос доступности требует
  оптимизации/индексации; это переходное решение для корректности.
- При смене длительности приёма исторический интервал без регистра
  вычисляется по **текущей** длительности. Перед массовым изменением
  длительности нужен отдельный регламент перерасчёта броней.
- Проверки исходников проведены статически; BSL не компилировался
  и не выполнялся на живой платформе 1С. PR следует держать
  черновым до проверки сценариев и конкурирующих записей.
