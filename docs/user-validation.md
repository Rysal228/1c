# Валидация пользователей приложения в 1С

## Что добавлено

`Catalogs/ПользователиПриложения/Ext/ObjectModule.bsl` содержит обработчик
`ПередЗаписью(Отказ)` модуля объекта справочника `ПользователиПриложения`.
Он выполняется при записи из формы **и** при `Объект.Записать()` из HTTP-сервиса.

- Телефон обязателен; формат 7XXXXXXXXXX. В форме разрешён ввод +7XXXXXXXXXX, при записи префикс + снимается.
- Для нового элемента `Код = Телефон`; для существующего прямое изменение кода/телефона запрещено.
- Проверяются конфликты по телефону, внешнему UUID и непустому `ИдентификаторMAX`.
- ФИО может быть пустым (не выдумываем его для MAX); длина каждого поля до 150 символов.
- `Наименование` формируется из фамилии и имени, при их отсутствии — телефон.
- Дата рождения может отсутствовать. Дата хранится в реквизите 1С; HTTP API отдаёт JSON null для пустой даты.

**Граница этой работы:** валидация записей независимого регистра `РолиПользователей` и права на управление ролями пока не менялись. Привязка MAX и проверка подлинности MAX **не** реализуются этим модулем: здесь проверяется только уникальность непустого идентификатора, а правила аутентификации обсуждаются отдельно.

## Установка в 1С (не выполняется автоматически при merge GitHub)

1. Создать резервную копию информационной базы 1С.
2. В Конфигураторе открыть **Справочники → ПользователиПриложения → Модуль объекта**.
3. Вставить содержимое `ObjectModule.bsl` из репозитория. Это новый модуль: отдельную общую серверную метадату создавать не нужно.
4. Проверить синтаксис модуля (встроенной проверкой конфигурации), затем обновить конфигурацию базы данных.
5. Выгрузить конфигурацию в файлы и обновить исходники/метаданные экспорта в GitHub. Текущий `ConfigDumpInfo.xml` и `1Cv8.cf` не пересоздавались этим PR.

## Проверки вручную в тестовой копии 1С

- Изменение имени существующего пользователя без изменения идентификаторов: запись успешна, `Наименование` обновляется, GET HTTP возвращает новое имя.
- Попытка сохранить телефон с недопустимыми символами или слишком короткий телефон: запись отклонена.
- Попытка изменить телефон, код или UUID существующего элемента: запись отклонена.
- Создание нового пользователя с телефоном, который уже существует: запись отклонена.
- Создание нового элемента с допустимым телефоном и пустым ФИО: запись успешна, `Наименование` равно телефону, UUID назначается автоматически.
- Дублирование непустого идентификатора MAX другого пользователя: запись отклонена.
- Повторный `PUT` из Django для одного из уже импортированных пользователей: запись должна оставаться успешной.
- GET пользователя без даты рождения: `birthday: null`.

Проверку на конкурирующие записи при больших нагрузках следует усилить отдельным механизмом блокировок/уникальных ограничений; проверка `НайтиПоРеквизиту` сама по себе не гарантирует атомарную уникальность для всех реквизитов при гонках.

## Дальнейшая архитектура

Данные профилей/ролей остаются в 1С. Django в целевой схеме — шлюз аутентификации/JWT; он не хранит копии пользовательских бизнес-полей.
