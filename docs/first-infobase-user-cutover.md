# Критический переход: первый пользователь информационной базы 1С

## Проверенные факты (18.10.2026)

Пользователь проверил на реальной 1С 8.5.1.1522:
- В тесте `ПолучитьСоставСтандартногоИнтерфейсаOData()` регистр
  `ПаролиПользователейПриложения` **отсутствует** в составе OData.
  **Это не замена проверке прав, а дополнительная защита.**
- `Конфигуратор → Администрирование → Пользователи` — **пустой список**.
- Текущая публикация `ServiceCar` имеет `ServiceCarAPI`, а новый
  `ServiceCarAuth` не отмечен. Публикация HTTP-сервисов по умолчанию
  отключена.
- Backend обращается к действующему 1С API без технических credentials
  по `http://host.docker.internal:8081/ServiceCar/hs/api` при
  `ONEC_ALLOW_UNAUTHENTICATED_INTERNAL=1`.

## Почему нельзя сейчас создать servicecar-auth

Когда в ИБ нет пользователей, анонимный вход может работать.
Платформа 1С **не разрешает анонимный доступ к ИБ, где созданы
пользователи**. Внесение первой учётной записи в продакшен ИБ
без предварительного изменения клиента Django может оборвать
профили и специалистов. Нельзя считать, что одна новая отдельная
публикация защитит старую: обе смотрят на ту же ИБ и список
пользователей общий.

Официальные источники:
- https://its.1c.ru/db/freshpub/content/56/hdoc — публикация сервисов с анонимным доступом, требования к пользователям ИБ.
- https://kb.1ci.com/1C_Enterprise_Platform/Guides/Administrator_Guides/1C_Enterprise_8.3.25_Administrator_Guide/Chapter_8._Setting_up_web_services_for_1C_Enterprise/8.9._Safety_while_using_Internet_services/8.9.1._Authentication/
- https://kb.1ci.com/1C_Enterprise_Platform/Tutorials/Practical_developer_guide_8.3/Lesson_22._Users_and_their_roles/Adding_users/In_Designer_mode/?language=en

## Порядок перехода (сначала только непроизводственная копия)

1. Снять согласованную и **проверенную** резервную копию ИБ и копию
   файлов публикации Apache (`default.vrd` и конфигураций с секретами).
   Не сохранять резервную копию в общедоступном веб-каталоге.
2. Поднять **отдельную тестовую копию** той же ИБ, с другим именем
   базы и другой Apache-публикацией/каталогом; проверить, что тест
   никаким URL не направлен в production.
3. В **копии** конфигурации создать платформенные роли:
   - системная административная роль с правами администрирования
     и полным доступом для восстановления доступа к Конфигуратору;
   - роль `ServiceCarAPIIntegration` только с необходимыми правами
     старого ServiceCarAPI (GET/PATCH профиля и roster и т.п.,
     основанными на реальном коде), без чтения регистра паролей;
   - `ServiceCarAuthVerifier` — только чтение пользователей,
     бизнес-ролей, регистра паролей и использование ServiceCarAuth,
     **без** прав на запись хеша/изменение пользователей.
4. Обновить конфигурацию **копии** базы (F7) до создания пользователей.
5. **Первым создать администратора ИБ с надёжным паролем** и
   системными правами. Проверить, что вход в Конфигуратор под ним
   работает и можно управлять учётными записями.
6. Создать два отдельных техпользователя ИБ:
   `servicecar-api` для старых операций и `servicecar-auth`
   для нового read-only password verifier. Никогда не использовать
   общую учётную запись администратора для интеграций.
7. **Сначала обеспечить для старого ServiceCarAPI защищённый канал
   (HTTPS с проверкой сертификата или другой подтверждённый
   защищённый туннель) в тестовой интеграции.** Сейчас
   `ONEC_BASE_URL` использует HTTP на `host.docker.internal:8081`;
   **нельзя отправлять по этому каналу Basic credentials**, даже если
   он внутренний. После этого настроить в **тестовом** Django
   для старого API `ONEC_API_USER=servicecar-api` и `ONEC_API_PASSWORD`
   через безопасное хранилище секретов (не GitHub/чат);
   `ONEC_ALLOW_UNAUTHENTICATED_INTERNAL` отключить после
   подтверждённого Basic-доступа. Текущий OneCUsersClient уже
   умеет Basic credentials, без обязательных изменений кода.
8. Проверить использование сертификата и старый профиль GET, PATCH только тестового пользователя,
   поиск специалистов и отрицательные проверки: запрос без Basic
   должен быть отклонён на тестовой ИБ; servicecar-api **не должен**
   иметь возможности читать регистр хешей.
9. **Отдельно**, не в старой публикации, настроить
   `ServiceCarAuth` только с HTTPS, Basic, ограничением доступа по
   сети и частоты. Проверить отказ неавторизованным вызовам,
   после этого проверить вход искусственного пользователя.
10. Документировать последовательность переноса в production
    как одну координированную операцию с согласованным окном
    обслуживания, критериями успеха и **проверенным планом
    восстановления**. Не создавать первого пользователя production
    до успешного прохождения всех тестов на копии.

## Обязательные проверки после переключения

- Старый профиль и механики работают с технической авторизацией;
- 1С без учетных данных запрещает доступ (новое ожидаемое поведение);
- `servicecar-api` не читает/пишет хеши;
- `servicecar-auth` не пишет хеши и не вызывает операции старого API;
- отдельная публикация ServiceCarAuth не включена в старый ServiceCar;
- обратная совместимость Django MAX, JWT и пользовательских связей;
- новые реальные пароли **не устанавливать** до принятия end-to-end
  решения по переключению логина и сбросу паролей.

## Безопасность и окружение

Не перепубликовывать `ServiceCar` и не менять старый `default.vrd`
без сохранённого варианта возврата. Откат возможного появления
первого пользователя ИБ сложнее, чем откат backend кода: **резервная
копия всей ИБ и тест восстановления обязательны**.

Все приведённые имена ролей/учётных записей — проектные имена;
не входят автоматически в состав 1С.

Отдельно помнить, что тест OData подтверждает состав объектов, но
не заменяет проверку фактического HTTP-доступа к OData с выбранными
правами технических пользователей.
