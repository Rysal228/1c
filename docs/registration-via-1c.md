# Регистрация нового пользователя через существующий ServiceCarAPI

## Что изменено в исходниках 1С

В `HTTPServices/ServiceCarAPI/Ext/Module.bsl` метод
`POST /ServiceCar/hs/api/user` уже создавал профиль и роли.
Теперь он дополнительно принимает необязательное поле
`password` **только при POST**. Если оно есть, процедура
`УстановитьПарольПриложения` записывает встроенный солёный
хеш в `РегистрСведений.ПаролиПользователейПриложения`
в той же транзакции, что и новый элемент справочника и его
назначения ролей. При ошибке 1С откатывает все три изменения.

Минимальная длина для создаваемого пароля изменена
с 12 до 8 символов, чтобы не нарушить существующую форму
регистрации Django. Максимальная длина — 128 символов.
Если локальная внешняя форма установки пароля `.epf`
имеет собственную проверку 12 символов, она пока остаётся
отдельным административным инструментом.

При отсутствии `password` прежний сценарий создания
профиля (например, миграционные команды) остаётся рабочим.
PUT/PATCH не принимают поле `password`: нельзя менять
пароль существующего пользователя без отдельной логики.

Старый заглушечный HTTP-маршрут `GET /user/profile` и его обработчик
`UserProfileGetProfile` **удалены из PR**: они не читали профиль и
не участвовали в рабочей бизнес-логике. Константный маркер
`passwordRegistration` не используется. После POST Django требует
`hasPassword:true`, вычисленный по фактической записи в регистре.

Дополнительно `GET /user/{phone}` теперь возвращает
поле `hasPassword: true/false` — **только признак наличия**
записи, не само сохраняемое значение. Django использует
его вместо устаревшего `has_usable_password()`.

## Что применить в Конфигураторе

Текстовая ветка в GitHub **не обновляет работающий файл базы 1С**
и сама по себе **не меняет `1Cv8.cf`**.
Из ветки `feat/onec-password-registration` перенести
изменённый модуль `HTTPServices/ServiceCarAPI/Ext/Module.bsl`
в одноимённый модуль HTTP-сервиса `ServiceCarAPI`
в Конфигураторе. Из дерева HTTP-сервиса `ServiceCarAPI` также
удалить только шаблон `UserProfile` (`/user/profile`),
не затрагивая `UserByPhone` (`/user/{phone}`), и перенести
обработчик без заглушечной функции. Новых HTTP-сервисов,
шаблонов или портов создавать не требуется. Проверить синтаксис и обновить конфигурацию
базы данных. После этого выгрузить актуальную конфигурацию
и текстовый дамп в 1C GitHub репозиторий.

Проверка без создания пользователей:
- `GET /ServiceCar/hs/api/user/7XXXXXXXXXX` должен содержать
  логическое поле `hasPassword` без значения хеша: это реальная
  проверка содержимого регистра, а не статическая константа.
- Прежний `POST /password/verify` продолжает возвращать
  `authenticated` по существующему паролю.

**Не отправлять регистрационный POST с реальным паролем
в историю команд терминала.** Новую регистрацию проверить
через форму сайта после развёртывания обоих изменений.

## Важная граница

Транзакция 1С охватывает профиль+роли+хеш **только внутри 1С**.
Транзакция Django охватывает `CustomUser`, роли и привязку `onec_id`
только внутри PostgreSQL. Общей распределённой транзакции
между двумя базами нет: при обрыве после успешного POST в 1С,
но до фиксации PostgreSQL, запись 1С может потребовать
ручной сверки. Не следует повторять регистрацию с новым UUID,
не проверив дубликат номера и externalId.

## Проверка кода регистрации перед обновлением Django

В **работающем модуле** `ServiceCarAPI` проверьте наличие следующих
трёх фрагментов (не достаточно одного поля `hasPassword`):

```bsl
Если Данные.Свойство("password", Значение) Тогда
```

```bsl
УстановитьПарольПриложения(Ссылка, ПарольРегистрации);
```

Второй вызов должен стоять **после** `Объект.Записать()` и
`ЗаписатьРоли(...)`, но **до** `ЗафиксироватьТранзакцию()`.

```bsl
Данные.Вставить("hasPassword", ЕстьПарольПриложения(Ссылка));
```

После обновления конфигурации 1С можно объединить Django PR #47,
прогнать тесты и выполнить первую регистрацию через форму сайта.
Новая регистрация действительно записывает данные, поэтому проверять
ее лучше на специально подготовленной тестовой учётной записи.
