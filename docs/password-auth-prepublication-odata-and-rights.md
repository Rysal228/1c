# Следующий безопасный шаг: права и аудит OData перед публикацией ServiceCarAuth

Подтверждено владельцем установки 1С 8.5.1.1522, Apache 2.4:
- ServiceCar: `/var/www/1c-servicecar/`, включён ServiceCarAPI, авто-публикация HTTP-сервисов отключена.
- Стандартный OData включён; веб-клиент и Analytics тоже включены.
- ServiceCarAuth существует в конфигурации, но не опубликован в ServiceCar.
- Хеш 224 символа записывается и читается из `ПаролиПользователейПриложения`
  с ресурсом Строка(1024), парная проверка проходит, пробная транзакция отменена.

**Угроза:** флажок `Publish standard OData interface` относится не к
вкладке HTTP-сервисы; состав опубликованных объектов OData регулируется
отдельно. `InformationRegister` может быть опубликован в OData.
Нельзя полагаться на `PasswordMode=true`, отсутствие стандартных команд
или скрытие HTTP-службы для сохранения конфиденциальности хеша.
Даже если доступ ограничен правами, отсутствие регистра в OData — полезный
дополнительный барьер.

## Шаг A — проверить состав OData без модификации

На тестовой копии либо в доверенном серверном контексте текущей
информационной базы (внешняя обработка с управляемой формой, как прежние
тесты) выполнить:

```bsl
&НаКлиенте
Процедура ПриОткрытии(Отказ)
    Сообщить(ПроверитьПубликациюПаролейВОData());
КонецПроцедуры

&НаСервереБезКонтекста
Функция ПроверитьПубликациюПаролейВОData()
    Состав = ПолучитьСоставСтандартногоИнтерфейсаOData();
    Для Каждого ОбъектМетаданных Из Состав Цикл
        Если ОбъектМетаданных = Метаданные.РегистрыСведений.ПаролиПользователейПриложения Тогда
            Возврат "ВНИМАНИЕ: регистр паролей присутствует в OData!";
        КонецЕсли;
    КонецЦикла;
    Возврат "OK: регистра паролей нет в составе OData.";
КонецФункции
```

Код ничего не меняет, не читает значения и не выводит хеш.
Если 1С на конкретной версии не компилирует глобальный метод,
использовать Синтакс-помощник, не продолжать без проверки.

Если регистр уже присутствует в OData, сначала выяснить какие другие
объекты использует текущая интеграция. Затем заменить состав OData на
строгий allowlist (без регистра паролей), используя
`УстановитьСоставСтандартногоИнтерфейсаOData`. **Нельзя просто
сбросить весь состав или выключить OData в рабочей публикации без
проверки зависимостей.** Отдельно проверить HTTP-доступ по OData с
анонимными и ограниченными правами.

## Шаг B — подготовить точечные права 1С

В репозитории `Rysal228/1c` в текущей выгрузке **нет метаданных ролей**.
Это не бизнес-роли `РолиПользователей` (перечисление и регистр):
речь о **метаданных Общие → Роли** платформы 1С.

1. В Конфигураторе создать роль `ServiceCarAuthVerifier` в `Общие → Роли`.
2. Дать только необходимые права:
   - `HTTP-сервис.ServiceCarAuth`: `Использование` (или
     аналогичное право на метод `PostPasswordVerify`);
   - `Справочник.ПользователиПриложения`: `Чтение`;
   - `РегистрСведений.РолиПользователей`: `Чтение`;
   - `РегистрСведений.ПаролиПользователейПриложения`: `Чтение`.
   Некоторые права `Использование` могут требоваться для типов/
   перечислений — решать после компиляции и теста минимальных прав.
3. НЕ давать этому техническому пользователю `Запись`, `Изменение`,
   `Администрирование`, `Полные права`, право `Использование`
   старого ServiceCarAPI, открытие внешних обработок.
**Перед созданием:** посмотреть `Администрирование → Пользователи`.
Если список системных пользователей ИБ **пустой**, не создавать
первого пользователя сразу в рабочей базе: появление аутентификации
может изменить поведение старых неавторизованных HTTP-вызовов.
Сперва проверить на копии ИБ и согласовать доступ к старому ServiceCarAPI.

4. Создать в `Администрирование → Пользователи` системного
   пользователя ИБ (не элемент справочника приложения) с именем
   **`servicecar-auth`**, сильным отдельным секретом и только этой
   ролью. Секрет нельзя публиковать в GitHub, присылать в чат
   или вставлять в команды с shell history.
5. Настроить *другую роль* для административной установки новых паролей,
   когда безопасная административная форма будет готова. Не давать
   права записи техническому пользователю, проверяющему пароль.

Проверить изменение прав в непроизводственной копии, затем аккуратно
перенести в рабочую базу. Не отключать существующему админу права.

## Шаг C — изоляция веб-публикации (ПОКА НЕ ВЫПОЛНЯТЬ)

Новая `ServiceCarAuth` будет отдельной публикацией Apache
с отдельным каталогом и включённым только одноимённым HTTP-сервисом;
подробности: `service-car-auth-private-publication.md`.
TLS, защита сети, гарантированная аутентификация ИБ, ограничения частоты
и проверка отсутствия anonymous-доступа обязательны до первой отправки
паролей пользователей.

Никакой миграции паролей, MAX, Django login/JWT, существующих
связей сейчас не выполняется.
