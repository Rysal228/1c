# Статистика менеджера — первая версия

## Контракт

`GET /ServiceCar/hs/api/orders/statistics?actorId=<uuid>&actorRole=admin&from=YYYY-MM-DD&to=YYYY-MM-DD`

Доступ проверяет `ЗаказАвтор` по справочнику пользователей и регистру ролей. Дополнительно `ЗаказМенеджер` требует `actorRole=admin`; чужие роли возвращают 403. URL статический и расположен перед `/orders/{id}` в метаданных HTTP-сервиса.

Период включителен, от 1 до 90 календарных дней. Django предлагает выбор 7/30/90 дней и проверяет JWT и активную роль до запроса к 1С.

Пример структуры ответа (значения берутся **только из базы**, а не из демоданных):

```json
{
  "period": {"from": "2026-10-01", "to": "2026-10-22", "days": 22},
  "summary": {
    "orders": 0,
    "completed": 0,
    "workAmount": 0,
    "occupancyPercent": 0
  },
  "ordersTrend": [{"date": "2026-10-01", "count": 0}],
  "statusDistribution": [{"code": "under_review", "name": "На рассмотрении", "count": 0}],
  "topWorkTypes": [{"id": "<uuid>", "name": "Диагностика", "count": 0}],
  "weekdayOccupancy": [{"weekday": 0, "weekdayName": "Пн", "busy": 0, "capacity": 0, "percent": 0}]
}
```

## Методика

- **Новых заказов:** число неудалённых документов `ЗаказыНаОбслуживание`, у которых стандартная `Дата` в выбранном диапазоне. Динамика строится по этому полю, отсутствующие дни возвращаются с нулём. Не использовать `ДатаЗаписи` для счётчика новых заказов.
- **Завершено:** из созданных в период заказов количество с *текущим* `СтатусЗаказа.КодСтатуса = "completed"`. Это не история даты завершения.
- **Стоимость работ:** сумма `Цена` строк `Работы` этих документов. Это **не поступившая выручка**: нет отдельного учёта платежей и возвратов.
- **Статусы:** распределение текущих статусов именно по созданным за период заказам.
- **Популярные работы:** максимум 7 видов работ по числу строк табличной части у созданных за период заказов.
- **Загрузка:** по **датам посещения** внутри периода, отдельно от фильтра даты создания. Для каждого рабочего дня перебираются возможные начала записи по `НастройкиЗаписи` и `НедельныйГрафик`. Стартовые интервалы, пересекающиеся с `БлокировкиЗаписи`, исключены из знаменателя; интервалы, пересекающиеся с `ЗанятыеИнтервалы` или датами неудалённых документов (для ранее созданных вручную записей), считаются занятыми. Неделя агрегируется по дням Пн–Вс. Загрузка — доля стартовых слотов, а не число обслуживаемых автомобилей/часов работы. В дни без доступной ёмкости `percent=0`, а фронтенд показывает «—» при `capacity=0`.
- Для исторических дней **нельзя** считать занятость через `availableSlots`, поскольку этот список намеренно исключает слоты в прошлом.

Нижеописанные меры не требуют изменения схемы базы 1С: используется один новый URL-шаблон HTTP-сервиса и существующие регистры/документы.

## Проверка и выкладка

1. Обновить `HTTPServices/ServiceCarAPI.xml` (URL `OrderStatistics`) и `HTTPServices/ServiceCarAPI/Ext/Module.bsl` вместе, не только модуль.
2. Применить изменения к тестовой базе через Конфигуратор, проверить **F7**, обновить конфигурацию БД и проверить публикацию HTTP-сервиса.
3. Запросить день без заказов: структура ответа содержит пустые массивы статусов/видов работ и значения ноль.
4. Создать заказ сегодня, но с `ДатаЗаписи` на другую дату: новый заказ должен попасть в динамику **сегодня**, а занятость — в дату записи.
5. Добавить/изменить статусы и строки работ, сверить расчёты после перезапроса; проверить пометку удаления.
6. Создать заказ непосредственно в 1С, убедиться, что занятость периода учитывает его; блокировка времени должна уменьшать ёмкость, а не повышать занятость.
7. Проверить вызов от `user` и `mechanic` и попытку запросить период более 90 дней.
8. Проверить объёмные интервалы 90 дней в тестовой базе: Django разрешает 30 секунд на этот конкретный запрос.

**Важно:** BSL-компиляцию, запросы к настоящей информационной базе и интеграционные проверки необходимо выполнить отдельно после переноса модуля: GitHub-проверка структуры не заменяет F7.
