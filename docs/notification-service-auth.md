# Служебный API уведомлений без пользователя менеджера

Совместно с обновлением backend после PR #74. Пулинг остаётся в Django:
никаких регламентных заданий и отправки в MAX из 1С не добавляется.

## Новые объекты

- Регистр сведений `НастройкиСервисаУведомлений`: непериодический, независимый;
  измерение `Ключ` (строка 10), ресурс `КлючДоступа` (строка 128, режим пароля).
  Для работы нужна запись `Ключ = main`; секрет создаётся при настройке базы,
  в исходниках, `1Cv8.cf` и метаданных его нет.
- `GET /ServiceCar/hs/api/notifications/orders` → минимальный список статусов.
- `GET /ServiceCar/hs/api/notifications/orders/{id}/recipient` → актуальный
  получатель конкретного заказа.

Оба метода до чтения заказов проверяют заголовок `X-ServiceCar-Notifications-Key`.
Ключи — 32–128 символов `A-Z a-z 0-9 _ -`, сравнение чувствительно к регистру.
Неверный/пустой ключ, отсутствие записи `main`, ошибка чтения настроек → 401.
Параметры actorId/actorRole, JWT пользователя и секрет в URL не заменяют ключ.
Все ответы имеют `Cache-Control: no-store`. Ответы и ключи не журналируются.
Разрешены только GET, никаких полномочий записи заказов новый ключ не даёт.

## Контракт

Лента возвращает массив записей:

```json
{
  "id": "UUID документа",
  "car": "UUID автомобиля",
  "ownerId": "UUID клиента или null",
  "orderNumber": "00000125",
  "carName": "Toyota Camry",
  "status": {"code": "in_progress", "name": "В работе"},
  "workStatus": {"code": "execution", "name": "Ремонт"}
}
```

Не возвращаются телефоны, ФИО, VIN, стоимость, описания, фотографии и исполнители.
`ownerId` заполнен, если владелец автомобиля совпадает с клиентом документа;
при расхождении — null и Django не ставит уведомление в очередь.

Проверка получателя возвращает `id`, `car`, `ownerId`, `eligible`,
`messengerUserId`. eligible=true только для существующего неудалённого заказа,
автомобиля без пометки удаления, того же владельца и активного неудалённого
пользователя с допустимым MAX ID. При расхождении владельца или неактивной
привязке eligible=false и MAX ID пустой. Отсутствующий/помеченный заказ → 404;
некорректный UUID → 400 после авторизации. Django также сверяет id/car/ownerId
с записью очереди непосредственно перед отправкой. Исторический заказ не должен
попасть новому владельцу автомобиля.

## Применение

1. Приостановить уже работающий cron уведомлений Django, сохранить очередь.
2. Загрузить из файлов **Configuration.xml**, метаданные нового регистра,
   **HTTPServices/ServiceCarAPI.xml** и модуль **ServiceCarAPI/Ext/Module.bsl**
   вместе. ConfigDumpInfo.xml содержит ссылки на новые объекты. Двоичный
   `1Cv8.cf` автоматически не пересобран — обновление по старому CF новые
   методы не установит.
3. Проверить конфигурацию F7 на используемой платформе, обновить конфигурацию
   БД, обновить/перезапустить HTTP-публикацию по обычной процедуре.
4. Сгенерировать ключ на сервере: `python -c 'import secrets; print(secrets.token_urlsafe(48))'`.
   В режиме Предприятия через «Функции для технического специалиста» открыть
   регистр «Настройки сервиса уведомлений». Создать запись main и вставить ключ.
   Поле маскируется, история изменений/поиск отключены; доступ к самому
   регистру должен иметь только доверенный оператор и серверный контекст.
   Маскирование не является разграничением прав.
5. В окружение Django записать тот же `ONEC_NOTIFICATIONS_SERVICE_KEY`, обновить
   backend и пересоздать контейнер. `MAX_ORDER_NOTIFICATIONS_MANAGER_ID` удалить.
   Не менять MAX_BOT_TOKEN, не создавать технического пользователя приложения.
6. Проверить методы и уведомление после изменения документа в клиенте 1С,
   затем вернуть cron раз в минуту. Подробные Docker-команды — в
   `backMag/docs/max-order-notifications.md` соответствующего изменения.

Доступ разрешает общий секрет **приложения**, а не учётная запись человека.
Увольнение/деактивация менеджера больше не влияет на опрос. Публичные методы
ServiceCarAPI сохраняют существующие правила и не получают новых прав.

## Проверка на тестовой базе

Перед запуском задать ONEC_NOTIFICATIONS_SERVICE_KEY в окружении процесса
из защищённой настройки, не включать его в аргументы командной строки.

```bash
python tools/smoke_notification_service.py --base-url http://host.docker.internal:8081/ServiceCar/hs/api
```

Скрипт только читает данные: проверяет 401 без ключа, с неверным ключом, при
подмене actor, положительный ответ и минимальный контракт, защиту второго
endpoint. Не печатает секреты/ответы/MAX ID и не отправляет сообщения.

Дополнительно вручную проверить:

1. Пустой/отсутствующий ключ настройки → 401, даже при правильном заголовке.
2. Отличающийся регистром ключ → 401; имя заголовка регистронезависимо.
3. Изменение статуса в форме и через сайт видно в следующем GET ленты.
4. Деактивация менеджера не влияет на оба служебных GET.
5. Изменение владельца, удаление заказа, отключение клиента и очистка MAX ID
   не допускают отправку старой очереди постороннему человеку.
6. Неизвестный заказ → 404; POST на новые пути не выполняет запись.
7. В логах reverse proxy/публикации не сохраняется заголовок ключа.

BSL не выполнялся и не компилировался в облачной среде; F7 и этот smoke test
нужно выполнить на установленной платформе перед включением фоновой задачи.

Сохранён совместимый внутренний HTTP-канал текущей установки. Он не шифрует
ключ: держать публикацию в доверенной закрытой сети. Для другого адреса Django
принимает только HTTPS. Не публиковать эти методы наружу и не передавать ключ
фронтенду. Для ротации приостановить задачу и заменить ключ на обеих сторонах.
