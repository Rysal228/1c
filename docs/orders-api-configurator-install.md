# Заказы на обслуживание — установка HTTP API в Конфигураторе (этап BSL)

Статус: **реализация в отдельной ветке GitHub, не установлена в информационную базу**. Проверка статической структуры проведена, компиляции/запуска в платформе 1С пока не было. Никакие существующие пользователи, пароли, MAX или автомобили на сервере 1С не обновляются этим PR автоматически.

## 1. Как перенести код в 1С без XML/CF-импорта

Ветка `feature/onec-orders-api-bsl` содержит:
- `HTTPServices/ServiceCarAPI/Ext/Module.bsl` — итоговый файл модуля сервиса с обработчиками заказов рядом с действующими пользователями, MAX и автомобилями.
- **`docs/order-handlers-to-paste.bsl`** — только **новая** часть BSL, начиная с комментария `// ===== API ЗАКАЗОВ`. Её удобнее копировать в Конфигуратор.
- `docs/orders-api-configurator-install.md` — настоящая инструкция.

Порядок ручной установки:
1. Сделать резервную копию ИБ и работать сначала с тестовой ИБ 1С.
2. Открыть **Конфигуратор → HTTP-сервисы → ServiceCarAPI → Модуль**.
3. Найти и **удалить две заглушки**, которые уже есть в твоём модуле: `Функция OrderWorkTypesGet(Запрос)` и `Функция OrderStatusesGet(Запрос)`, каждая со своим `КонецФункции`. Не удалять другие функции.
4. В конец модуля вставить содержимое [`docs/order-handlers-to-paste.bsl`](https://github.com/Rysal228/1c/blob/feature/onec-orders-api-bsl/docs/order-handlers-to-paste.bsl). Заново импортировать весь ServiceCarAPI или конфигурацию **не надо**. Вставляемый фрагмент определяет обе удалённые функции и все новые обработчики.
5. Создать HTTP URL-шаблоны ниже через дерево метаданных ServiceCarAPI. Два уже имеющихся (`/order-work-types`, `/order-statuses`) **не дублировать**.
6. Сохранить, **Конфигурация → Проверить конфигурацию**, исправить сообщения компиляции, `F7` обновить ИБ, опубликовать HTTP-сервис при необходимости.
7. В режиме Предприятия проверить статусы, виды работ и расписание. Прогнать smoke-тесты, только после этого менять бэкенд.
8. После успешной локальной проверки **выгрузить обновлённую конфигурацию из Конфигуратора в GitHub** (с реальными UUID созданных вручную URL-шаблонов).

Файл GitHub нельзя просто «смержить и запустить» — работающий конфигуратор 1С не подхватит его сам.

## 3. Контракт безопасности

К каждому запросу Django-клиент `OneCOrdersClient` добавляет query параметры:
- `actorId` — нативный UUID справочника `ПользователиПриложения`, берётся **исключительно** из JWT Django;
- `actorRole` — активная роль (`user`, `mechanic`, `admin`), уже выбранная и проверенная Django.

BSL повторно проверяет пользователя, его `Активен` и наличие активной роли в регистре `РолиПользователей`. Ссылка клиента на собственный заказ и собственный автомобиль проверяется в 1С. Менеджеру (`admin` = перечисление `Менеджер`) разрешены изменения статусов, специалисту — только чтение.

**Критически важно:** эти query-параметры **не являются подписью или самостоятельной аутентификацией**. Любой, имеющий прямой доступ к 1С HTTP API, технически может подставить `actorId/actorRole` реально существующего пользователя. Поэтому HTTP-публикация 1С должна быть доступна только доверенному Django (правила сети, firewall, локальная публикация; при доступе между машинами — полноценная серверная аутентификация). Не выпускать сервис в публичный интернет. Это обязательное условие для эксплуатации.

## 4. Логика, реализованная на уровне HTTP

- Каталоги возвращают реальные UUID 1С и `code` статусов; не используются Django PK.
- Документ — **`Документы.ЗаказыНаОбслуживание`**, табличная часть `Работы.ВидРабот` — именно твоё имя реквизита.
- Только `user` создаёт заказ собственного **активного** автомобиля. Дата/время записи обязательны, работы **не обязательны**. По умолчанию статусы: `under_review`, `waiting_manager_review`, `unpaid`.
- Каждая добавленная строка работы обязана ссылаться на настоящий элемент `Справочники.ВидыРабот`. Запрещён `workTypes: ["свободный текст"]`, а также `works[].name`. `works: []` допустим. Дубли вида работ не допускаются; ID строки UUID.
- Пользователь не может менять цену; менеджер может. При пустом списке работ сумма 0. Название работы берётся из справочника.
- Менеджер назначает только активных пользователей с ролью `mechanic`, без дублей.
- Любой существующий статус можно назначить менеджером напрямую через отдельный POST; **никакой жёсткой матрицы и автоматической смены других статусов**. Оплата самостоятельная, не блокирует `execution`.
- Свободные интервалы рассчитываются по `НастройкиЗаписи`, `НедельныйГрафик`, `БлокировкиЗаписи` и `ЗанятыеИнтервалы`. Проверяется час, день, шаг и пересечения; сохранение + запись брони — в одной управляемой транзакции с исключительной блокировкой регистра. Отказ/изменение статуса сами по себе **не освобождают** слот: статусы независимы.
- Клиент видит только свои заказы. Менеджер и специалист пока видят все, как в действующем Django. Клиент не получает `ownerPhone`, специалист не получает цену работ/сумму; интерфейсная фильтрация будет оставаться на Django.
- Пока список получаем со всеми документами, а фильтрация по большинству полей — после выборки в 1С. Для больших объёмов нужен переход на серверную фильтрацию/пагинацию; не считать этот вариант оптимальным по производительности.

## 5. Примеры проверок (внутренний API, после публикации)

Ниже `<uuid>` — именно реальные UUID из 1С, `actorId` — активный пользователь соответствующей роли. Тестировать через защищённую локальную сеть, не в браузере пользователя.

```text
GET /ServiceCar/hs/api/order-work-types?actorId=<uuid>&actorRole=user
GET /ServiceCar/hs/api/order-statuses?actorId=<uuid>&actorRole=admin
GET /ServiceCar/hs/api/order-work-statuses?actorId=<uuid>&actorRole=admin
GET /ServiceCar/hs/api/order-payment-statuses?actorId=<uuid>&actorRole=admin
GET /ServiceCar/hs/api/order-schedule?actorId=<uuid>&actorRole=user
GET /ServiceCar/hs/api/order-availability?date=2026-10-22&actorId=<uuid>&actorRole=user
GET /ServiceCar/hs/api/orders?actorId=<uuid>&actorRole=user
```

Создать заказ без работ:
```json
{
  "car": "3bc5c300-d1e0-471e-8f4c-cc1f8610db8c",
  "appointmentAt": "2026-10-22T09:00:00+07:00",
  "description": "Осмотр без выбранного вида работ",
  "works": []
}
```
UUID автомобиля здесь **образец формата**, не гарантированно существующий объект. Дата теста должна быть будущей относительно момента исполнения и в рабочем графике ИБ. Реальные значения брать из 1С.

Создать с одной справочной работой:
```json
{
  "car": "3bc5c300-d1e0-471e-8f4c-cc1f8610db8c",
  "appointmentAt": "2026-10-22T10:30:00+07:00",
  "works": [{"workTypeId": "8449407b-315d-4fa9-b058-2727c43a1b78"}]
}
```

Перевести в произвольный статус заказа:
```json
{"statusId": "575274d0-f291-4826-8dc5-97cfa32d9ab1", "refusalReason": ""}
```

## 6. Что **не подтверждено** и остаётся до production cutover

1. **BSL не компилировался в настоящем Конфигураторе**, не тестировался под твоей версией платформы 1С. Ветки GitHub не заменяют тесты (первое действие — проверка конфигурации). Если компиляция выдаст конкретную строку/ошибку — сообщи её, исправим в ветке.
2. В GitHub **не видно записи данных** в справочниках/регистрах; нужно лично убедиться, что начальные статусы, виды работ, недельный график и настройка `main` заполнены в информационной базе.
3. **Часовой пояс:** дата во внешнем JSON явно маркируется `+07:00`, предполагается местное время 1С = `Asia/Krasnoyarsk` как в Django. Проверить настройки ОС/сервера 1С, особенно если база опубликована на другой машине; при несовпадении требуется явная конверсия. Не запускать при разном часовом поясе.
4. Бронирование и проверки сейчас выполняются **через HTTP-методы**. Редактирование документов напрямую в автоматической форме Предприятия может обойти эти проверки и оставить некорректные слоты. До вынесения общих инвариантов в модуль объекта/общий модуль **не редактировать вручную даты заказов и связанные записи регистров в Предприятии**. Это отдельный обязательный этап перед разрешением ручного редактирования.
5. Нет гарантий атомарности повторного POST при сетевом обрыве после успешной записи: нужны идемпотентные ключи запросов для боевого режима или повторная проверка списка созданных документов при таймауте.
6. Нужно синхронизировать существующий Django API и Angular: обновить номера статусов/видов на UUID, убрать произвольные названия работ, сохранить разрешения фильтров на Django; обновить `cars/views.py` и связи чатов с заказами. **Текущий рабочий Django ещё использует PostgreSQL**, нельзя переключить без этой миграции.
7. Нужны автотесты сценариев на **настоящей 1С**: две конкурентные записи на один слот; клиент пытается получить чужой заказ; механик пытается сменить статус; изменение цены клиентом; выбор несуществующего вида работ; статус `completed` не освобождает запись; назначение механика/просмотр цены.

Мерж 1С PR сам по себе **не публикует новые обработчики** и не означает, что сайт уже использует 1С заказы.
