# ServiceCarAuth — закрытый сервис проверки пароля веб-приложения

Статус: **DRAFT / НЕ ПУБЛИКОВАТЬ**. На 1С 8.5.1.1522 уже пройдена
проверка платформенного PBKDF2 и запись/чтение хеша (224 символа)
из регистра `ПаролиПользователейПриложения` (Строка(1024)).
Следующий этап — отдельный HTTP-сервис с **одним** методом проверки пароля,
а не установка нового пароля и не замена действующей авторизации.

## Дополнительная диагностика SSL и размещения сертификатов

По `apache2ctl -M` доступны `auth_basic_module` и
`authn_file_module`, но **`ssl_module` пока не подключён**.
`service-car-frontend` — контейнер Nginx, который принимает 443;
его host bind-mount сертификатов:
`/opt/service-car/certbot/conf` → `/etc/letsencrypt`.
В репозитории frontend HTTPS-сертификат задан через
`/etc/letsencrypt/live/cherser-car.site/{fullchain,privkey}.pem`,
а значит на хосте предполагаются
`/opt/service-car/certbot/conf/live/cherser-car.site/fullchain.pem`
и `privkey.pem`. **Наличие и права этих файлов нужно подтвердить
на сервере**, не показывая их содержимое.

Предпочтительный кандидат при сохранении одной 1С-публикации:
**дополнительный узкосетевой TLS VirtualHost того же Apache 2.4**
на адресе Docker-host-gateway и отдельном порту (условно 8443),
где разрешён только `ServiceCarAuth` и есть
Apache Basic authentication (`AuthUserFile` вне web root).
В прежнем HTTP VirtualHost `:8081` запретить
`/ServiceCar/hs/auth/` и `/servicecar1c/hs/auth/`
через `LocationMatch`, **до** включения ServiceCarAuth в default.vrd.
Это два сетевых входа в *одну* публикацию той же ИБ, не две базы и
не отдельный Apache.

Ещё не определены адрес Docker host gateway, способ проверить TLS
hostname из backend-контейнера и фактическое наличие сертификата.
Не включать новую службу до end-to-end проверки TLS, Apache Basic,
прямого запрета HTTP-пути на `:8081`, ограничения частоты запросов
и отсутствия утечек через другие алиасы. **Само наличие Basic
не обеспечивает защиты без TLS**.

Текущее BSL `ServiceCarAuth` требует пользователя **информационной
базы** `servicecar-auth`. Для выбранной Apache Basic-схемы его
нужно адаптировать в отдельном ревью: сейчас он не совместим
с отсутствием системных пользователей ИБ, и наличие HTTP-заголовка
Basic само по себе не доказывает проверку пароля.

Безопасные команды подтверждения:
```bash
docker exec service-car-backend getent hosts host.docker.internal
sudo test -s /opt/service-car/certbot/conf/live/cherser-car.site/fullchain.pem && echo CERT_OK
sudo test -s /opt/service-car/certbot/conf/live/cherser-car.site/privkey.pem && echo KEY_OK
```

## Проверка продакшн-сервера (18.10.2026)

Получены только читающие диагностические сведения от администратора:
- `docker-proxy` слушает 80/443 с контейнером `service-car-frontend`.
- `apache2` слушает `*:8081`, VirtualHost объявлен в
  `/etc/apache2/sites-enabled/000-default.conf`.
- Публикация 1С описана **не** в этом vhost, а в
  `/etc/apache2/apache2.conf` (около строк 183–193):
  `ManagedApplicationDescriptor /var/www/1c-servicecar/default.vrd`,
  `Alias /ServiceCar`.
- `frontMag/nginx.conf` (ветка `dev`) проксирует `/api/`, `/admin/`,
  `/ws/` к Django; маршрута к 1С в репозитории нет.
- В `Администрирование → Пользователи` **нет системных пользователей**.
  Не создавать первый системный пользователь production ИБ до проверенного
  перевода действующего Django API с анонимного доступа.
- Текущий `ServiceCarAuth` BSL требует `servicecar-auth` как системного
  пользователя: он пока **не совместим** с пустой таблицей пользователей
  и не станет рабочим просто от включения галочки.
- `*:8081` — прослушивание на всех интерфейсах, **не** доказательство
  внешней доступности: отдельно проверить firewall/ACL. Если использовать
  Nginx на 443, запросы к auth-сервису по 8081 нельзя оставлять в обход
  аутентификации/TLS.
- Старый клиент Django ходит на `http://host.docker.internal:8081/ServiceCar/hs/api`.
  **Нельзя передавать реальные пользовательские пароли** по этому
  незашифрованному каналу.

**Решение по защите ещё не принято.** Не менять автоматически
публикацию, Nginx, Apache, Django, JWT или MAX. Нельзя считать
новую публикацию единственно возможным вариантом; можно выбрать
другой верифицируемый защищённый маршрут с конечной авторизацией и
запретом обхода. Не создавать публично доступный auth-метод с
единственной проверкой пришедшего из клиента заголовка `Authorization`:
такой заголовок подделывается.

Для уточнения только чтение без секретов:
```bash
sudo sed -n '175,205p' /etc/apache2/apache2.conf
sudo ufw status verbose
docker exec service-car-frontend nginx -T 2>&1 | grep -nE 'listen|server_name|location|proxy_pass' 
```
Последняя команда только просматривает строки настроек, но вывод может
показывать домены и другие чувствительные данные — редактировать перед
передачей; полный конфиг с паролями не отправлять.

## Подтверждённая существующая публикация (18.10.2026)

На рабочей 1С 8.5.1.1522 с Apache 2.4 уже настроена публикация:
- имя **ServiceCar**;
- каталог **/var/www/1c-servicecar/**;
- клиентский вход: включён;
- стандартный OData: включён;
- Analytics: включён;
- публикация **Web services** по умолчанию: включена;
- публикация **HTTP services** по умолчанию: **выключена**;
- в таблице HTTP services только **ServiceCarAPI / api**, сервис включён.

**Ничего из этого не выключать и не перепубликовывать для миграции
паролей**: существующая система использует данную публикацию. Важнейший
инвариант после добавления ServiceCarAuth в метаданные — старый
`ServiceCar` по-прежнему публикует **только ServiceCarAPI**; у
`ServiceCarAuth` на старой публикации флажок должен быть выключен.
Опция Web services по умолчанию не включает HTTP-сервисы.

## План новой отдельной публикации (ещё не выполнять до проверки BSL)

Для новой публикации предложены **новые** имя и каталог, которые не должны
совпадать со старыми:
- Имя: `ServiceCarAuth`
- Web server: `Apache 2.4`
- Directory: `/var/www/1c-servicecar-auth/`

В форме публикации **нового** виртуального приложения:
- Publish client application entry-point URL: **выкл**
- Publish standard OData: **выкл**
- Publish Analytics: **выкл**
- Publish web services by default: **выкл**, в списке — ничего
- Publish HTTP services by default: **выкл**,
  **ServiceCarAPI = выключено, ServiceCarAuth / auth = включено**.

Важное замечание: эта форма не включает HTTPS сама. Нужно отдельно
настроить Apache/reverse proxy на HTTPS, ограничить сеть, проверить
сертификат и что HTTP-служба опубликована в этом новом адресе
**без возможности пользоваться анонимным доступом**.

**До публикации:**
- сохранить защищённую копию действующего `default.vrd` и Apache
  конфигурации (они могут содержать служебные пароли);
- проверить действующий HTTPS/прокси и подтвердить сетевой маршрут
  Django → Apache 2.4 по HTTPS;
- создать ИБ пользователя `servicecar-auth` с узкими правами только на
  чтение профилей/ролей/хешей; без разрешений записи;
- убедиться, что в новом `default.vrd` в строке `ib` нет
  `Usr`/`Pwd`, которые могут дать обход Basic-аутентификации;
- предварительно выполнить проверку синтаксиса нового BSL на
  **тестовой копии** 1С 8.5.1.1522.

После публикации сначала проверить **отказы** без Basic, с неверным Basic,
через старую публикацию; затем пробный пароль **только тестового**
пользователя. Не использовать реальные пароли до прохождения всех проверок.

## Что добавлено в исходники

- `HTTPServices/ServiceCarAuth.xml` — новый HTTP-сервис, `RootURL=auth`,
  POST URL-шаблон `/password/verify`.
- `HTTPServices/ServiceCarAuth/Ext/Module.bsl` —
  `PasswordVerifyPost(Запрос)`. Проверяет обязательный заголовок
  Basic, а также текущего пользователя ИБ с точным именем
  `servicecar-auth` (дополнительная fail-closed проверка).
  Ни хеш, ни введённый пароль в ответ не включаются и не логируются.
- `Configuration.xml` — регистрация нового метаобъекта.

**Не вставлять** `PasswordVerifyPost` в старый анонимный
`ServiceCarAPI`, не включать `ServiceCarAuth` в его URL-шаблоны.

## Публикация — критически важно

В 1С публикация задаётся **для информационной базы**; даже новый
HTTP-сервис может автоматически стать доступным через СТАРЫЙ
анонимный адрес, если на публикации стоит
`httpServices publishByDefault="true"`.

Поэтому **до** установки нового HTTP-сервиса в рабочую
конфигурацию нужно:

1. Сделать резервную копию ИБ и сохранить исходные файлы публикации.
2. В конфигураторе выбрать публикуемые HTTP-сервисы **явно**:
   у старой публикации `ServiceCar` снять флажок
   «Публиковать HTTP-сервисы по умолчанию», оставить только
   `ServiceCarAPI` (не `ServiceCarAuth`). Проверить конечную
   конфигурацию `default.vrd` и выполнение прежнего API.
3. Подготовить ОТДЕЛЬНУЮ публикацию этой же ИБ (например
   `ServiceCarAuth`) со своим `default.vrd`. В ней
   `publishByDefault=false`, включён **только ServiceCarAuth**,
   `ServiceCarAPI` и все прочие сервисы отключены.
4. Создать технического пользователя **информационной базы**
   с именем **в точности `servicecar-auth`**, сильным
   уникальным паролем и минимальными правами для чтения
   `ПользователиПриложения`, `ПаролиПользователейПриложения`,
   `РолиПользователей`. Не давать изменение регистра,
   изменение пользователей, административные права; проверить
   точный состав прав в 1С. Его пароль не хранить в GitHub.
5. Убедиться, что в `default.vrd` отдельной auth-публикации
   **НЕТ `usr=`/`pwd=` служебного пользователя в строке `ib`**,
   а анонимный пользователь публикации не имеет прав чтения хешей.
   Basic-заголовок должен быть аутентифицирован платформой 1С.
   Кодовая проверка имени пользователя и наличия Basic не заменяет
   такую аутентификацию (header сам по себе не доказательство).
6. Настроить HTTPS на сервере публикации с сертификатом, которому
   доверяет backend (никакого `verify=False`), сетевые правила,
   запрещающие запросы извне Django/доверенной сети, запрет
   логирования тела запроса, парольных заголовков и секрета Basic.
   На прокси поставить ограничения размеров тела, частоты попыток
   входа по IP/пользователю. Проверить также, что старый HTTP порт
   8081 **не** предоставляет этот endpoint.
7. **Не включать до проверки**. Протестировать, что без Basic
   auth-сервис не проверяет пароль, с неверными служебными
   реквизитами — тоже, а старая анонимная публикация не маршрутизирует
   `/hs/auth/password/verify`. Только затем разрешать запрос
   из Django на HTTPS.

Конфигурация `default.vrd` (схема *только* фрагмента, не копировать
без проверки фактического файла):
```xml
<!-- СТАРАЯ публикация ServiceCar: только старый сервис -->
<httpServices publishByDefault="false">
  <service name="ServiceCarAPI" rootUrl="api" enable="true" />
</httpServices>
```

```xml
<!-- НОВАЯ публикация ServiceCarAuth: только закрытая проверка -->
<httpServices publishByDefault="false">
  <service name="ServiceCarAuth" rootUrl="auth" enable="true" />
</httpServices>
```

`base` и параметры соединения ИБ в каждом `default.vrd` задаются
настройками конкретной инсталляции; два опубликованных адреса
должны вести в **одну и ту же** нужную ИБ. НЕЛЬЗЯ незаметно
переопубликовать рабочий `ServiceCar` вместо нового адреса.

Пример будущего URL, **только если** имя новой публикации выбрано
`ServiceCarAuth`:
`https://<внутреннее-доверенное-имя>/ServiceCarAuth/hs/auth/password/verify`.
Это пример, фактический хост/путь нужно подтвердить.

## Контракт

Только технический backend через Basic по HTTPS:
```json
{"phone":"79135552525","password":"<secret>"}
```
- Верный пароль действующего пользователя с ролями: HTTP 200,
  `{"authenticated":true,"onecId":"<native-uuid>","phone":"79135552525","isActive":true,"roles":["user"]}`.
- Неверный пароль/нет записи/неактивный пользователь: HTTP 200,
  `{"authenticated":false}`.
- Запрос без надлежащих служебных прав: HTTP 403/401.
- Ошибка обработки — HTTP 500, без паролей или диагностических деталей.

Ограничение текущего BSL: возможны различия времени для
неизвестного пользователя и неверного пароля. Для защиты от
перебора и перечисления **обязательны** rate limits, доп. контроль
доступа и наблюдаемость по неуспешным попыткам (без секретов).

Django: отдельный клиент `OneCPasswordAuthClient` уже добавлен в
`backMag` PR #45; для будущего запроса нужны настройки
`ONEC_AUTH_VERIFY_URL`, `ONEC_AUTH_API_USER`,
`ONEC_AUTH_API_PASSWORD`. Ничего пока не задавать в production.
**AuthService.login, регистрация, JWT refresh, MAX не изменены**.
