# Перенос заказов в 1С через Конфигуратор — технический контракт (этап 1)

**Статус:** проектирование для ручной настройки; НЕ готовая конфигурация, НЕ инструкция загрузить XML. Основой служат `main` 1С и `master` backMag на 21.10.2026. До окончания ручного создания и smoke-тестов НЕ переключать Django.

## 0. Граница ответственности

- **1С** — единственный источник заказов, вида/стоимости работ, назначения специалистов, статусов заказа/работ/оплаты, переходов, правил редактирования, графика работы, интервалов записи, блокировок и доступности. 1С перепроверяет авторство, роль и все инварианты при любом изменении.
- **Django** — JWT, выбор активной роли, внешний URL `/api/v1/orders/`, сериализация запросов/ответов для Angular, ограничение видимости. Django НЕ хранит и НЕ принимает решений по статусам, ценам и слотам после cutover.
- **Чаты** — отдельная подсистема Django: комнаты/сообщения/вложения остаются в PostgreSQL, но `ChatRoom.order` впоследствии заменяется на `order_id UUID` без FK, и доступ проверяется по заказу из 1С.
- **Пользователи, марки, модели, автомобили** — уже существующие ссылки на справочники 1С. НЕ создавать дубли и дополнительные внешние ID.
- Старые таблицы заказов Django нельзя удалить до переключения всех зависимостей (`cars.views`, `chats.*`, serializers, admin) и проверки сценариев. Никаких автоматических очисток.

## 1. Что создать в Конфигураторе вручную

Ниже **имена метаданных являются контрактом** для следующего этапа BSL и HTTP API. Синонимы свободные. UUID метаданных сгенерирует Конфигуратор; **не копировать UUID из файлов GitHub**.

### 1.1. Справочники (неподчинённые, без иерархии)

| Справочник | Реквизиты | Стандартные |
|---|---|---|
| `ВидыРабот` | Нет дополнительных; `Наименование` строки 100 | Код авто, Наименование обязательно |
| `СтатусыЗаказов` | `КодСтатуса`: Строка(50), `Начальный`: Булево, `ТребуетОплаты`: Булево | Наименование 100 |
| `СтатусыРабот` | `КодСтатуса`: Строка(50) | Наименование 100 |
| `СтатусыОплаты` | `КодСтатуса`: Строка(50) | Наименование 100 |

`КодСтатуса` должен быть уникальным (контроль программно/дополнительный индекс). Не ориентироваться на автонумеруемый стандартный `Код`. Возвращать из API нативный UUID ссылки и стабильный `code`; смена отображаемого `Наименования` не должна ломать логику.

Данные для заполнения:
- `СтатусыЗаказов`: `under_review` / На рассмотрении (`Начальный=Истина`), `in_progress` / В работе, `completed` / Завершен.
- `СтатусыРабот`: `waiting_manager_review`, `manager_review`, `waiting_arrival`, `intake`, `owner_approval`, `waiting_payment`, `execution`, `owner_visit`, `refused`. Названия соответственно: Ожидание проверки менеджером; Проверяется менеджером; Ожидание прибытия авто в сервис; Приёмка; Согласование с владельцем; Ожидание оплаты; Специалисты выполняют заказ; Владелец должен явиться в сервис; Отказано.
- `СтатусыОплаты`: `unpaid` / Не оплачено; `paid` / Оплачено.

Не использовать `Перечисление` для редактируемых администратором статусов/видов работ; существующее `Перечисления.РолиПользователей` использовать повторно как фиксированный список ролей.

### 1.2. Документ `ЗаказыНаРемонт`

Создать **Документы → ЗаказыНаРемонт**. Включить в подсистему `Автосервис`. Нумерация стандартная платформы, уникальность номера в пределах года или сквозная (выбрать сквозную для совпадения с сайтом). `Номер` и `Дата` — стандартные реквизиты, НЕ создавать вручную.

| Реквизит документа | Тип | Назначение |
|---|---|---|
| `Клиент` | `СправочникСсылка.ПользователиПриложения` | Владелец заказа |
| `Автомобиль` | `СправочникСсылка.Автомобили` | Только активный автомобиль этого клиента |
| `СтатусЗаказа` | `СправочникСсылка.СтатусыЗаказов` | Текущее состояние |
| `СтатусРабот` | `СправочникСсылка.СтатусыРабот` | Этап процесса |
| `СтатусОплаты` | `СправочникСсылка.СтатусыОплаты` | `unpaid` / `paid` |
| `ДатаЗаписи` | Дата (состав: дата+время) | Пустая дата = без записи |
| `Описание` | Строка, неограниченной длины | Примечания |
| `ПричинаОтказа` | Строка, неограниченной длины | Причина отклонения |
| `ТелефонКлиентаСнимок` | Строка(20) | Исторические данные |
| `ИмяКлиентаСнимок` | Строка(450) | Исторические данные |
| `МаркаСнимок` | Строка(100) | Исторические данные |
| `МодельСнимок` | Строка(100) | Исторические данные |
| `МаркаАвтомобиля` | `СправочникСсылка.МаркиАвтомобилей` | Снимок нативной ссылки |
| `МодельАвтомобиля` | `СправочникСсылка.МоделиАвтомобилей` | Снимок нативной ссылки |
| `ГодВыпускаСнимок` | Число(4,0) | Исторический год |
| `VINСнимок` | Строка(64) | Исторический VIN |
| `ГосНомерСнимок` | Строка(20) | Исторический госномер |

Две табличные части:
- `Работы`: `ВидРаботы` (необязательная ссылка на `ВидыРабот`), `Название` (Строка 100, обязательно), `Цена` (Число 12,2, неотрицательная), `ИдентификаторСтроки` (Строка 36, UUID на уровне приложения для стабильного `works[].id`; при копировании выдавать новый). Повтор одного `ВидРаботы` запрещён; пользовательские работы без ссылки разрешены.
- `Специалисты`: `Специалист` (`СправочникСсылка.ПользователиПриложения`); дубли запрещены; проверять `Активен` и наличие роли `mechanic` в регистре `РолиПользователей`.

Важно: **не использовать имя реквизита `Владелец`** — ранее оно вызвало конфликт со стандартными реквизитами справочника.

### 1.3. Регистры сведений

Все ниже — **независимые, непериодические**, данные в одной ИБ 1С. В реальных формах настройка `ВремяНачала`/`ВремяКонца` хранится в **минутах от полуночи** целым числом 0…1440 (не в типе `Дата`), чтобы избежать неоднозначности даты времени.

| Регистр | Измерения | Ресурсы |
|---|---|---|
| `НастройкиЗаписи` | `Ключ` Строка(10), всегда `main` | `ДлительностьМинут` Число(4,0) = 60; `ИнтервалМинут` Число(4,0) = 30 |
| `НедельныйГрафик` | `ДеньНедели` Число(1,0) 0=пн…6=вс | `Рабочий` Булево; `НачалоМинут` Число(4,0); `КонецМинут` Число(4,0) |
| `БлокировкиЗаписи` | `Дата` Дата (без времени), `НачалоМинут` Число(4,0), `КонецМинут` Число(4,0) | Нет; пересечения проверяются кодом |
| `ЗанятыеИнтервалы` | `Дата` Дата (без времени), `НачалоМинут` Число(4,0), `ИдентификаторИнтервала` Строка(36) | `КонецМинут` Число(4,0), `Заказ` `ДокументСсылка.ЗаказыНаРемонт` (пустая ссылка для занятого времени без заказа) |
| `ПереходыСтатусовЗаказов` | `ИзСтатуса` ссылка на СтатусыЗаказов; `ВСтатус` ссылка; `Роль` `ПеречислениеСсылка.РолиПользователей` | `Разрешен` Булево |
| `ПереходыСтатусовРабот` | `ИзСтатуса` ссылка на СтатусыРабот; `ВСтатус` ссылка; `Роль` перечисление РолиПользователей | `Разрешен` Булево |
| `ДоступКФильтрамЗаказов` | `Роль` перечисление РолиПользователей; `КлючФильтра` Строка(30) | `Разрешен` Булево |

Проверки `ДлительностьМинут` и `ИнтервалМинут`: 5…1440 и интервал не длиннее длительности; `Рабочий`: начало раньше конца, день 0…6. Для времени в пределах дня запретить перенос через полночь. `БлокировкиЗаписи` не должны пересекаться между собой или с занятыми периодами по принятой политике редактирования графика.

При создании нового документа с выбранной `ДатаЗаписи`: **в одной транзакции** взять управляемую блокировку по календарной дате для регистра `ЗанятыеИнтервалы`, перепроверить рабочие часы, дискретность начала, будущее время, все блокировки и занятые интервалы; только потом сохранить документ и занятый интервал. При переносе снять старую запись в той же транзакции, при отказе — освободить. Простая проверка свободного времени отдельным GET НЕ защищает от гонки двух клиентов.

### 1.4. Первичное заполнение графика

- Понедельник–пятница: `Рабочий=Истина`, `НачалоМинут=540` (09:00), `КонецМинут=1200` (20:00).
- Суббота, воскресенье: `Рабочий=Ложь`.
- Длительность записи 60 минут, интервал старта 30 минут.
- Мощность записи сохраняем как сейчас: **один глобальный занятый слот**, а не отдельные слоты по каждому механику. Изменение мощности — отдельная бизнес-задача.

## 2. Бизнес-правила без изменений

### 2.1. Создание

Только активная роль `user`. Запись по автомобилю из справочника `Автомобили`, `Автомобиль.ВладелецАвтомобиля=Клиент`, `Автомобиль.ВАрхиве=Ложь`. Не менять автомобиль в существующем заказе. При создании: `under_review`, `waiting_manager_review`, `unpaid`; работы обязательны, цена по умолчанию 0; сохранить данные клиента и машины в снимках, время занять. `id` заказа = собственный UUID ссылки документа 1С. `orderNumber` = стандартный номер документа, выдаваемый 1С; не генерировать и не хранить второй номер в Django.

### 2.2. Разрешения на редактирование (роль + стадия)

- `user` может править работы/описание/запись **только своего** заказа в `under_review + waiting_manager_review`; не может назначать специалистов или менять цены/статус оплаты.
- `admin` может править работы и цены только в `in_progress + owner_approval`; запись в `under_review + manager_review`; специалистов в любом `in_progress`; описание в любом не завершённом заказе; оплату только в `in_progress + waiting_payment`.
- `mechanic` не изменяет этапы, цены, специалистов, оплату и работы через текущий API. Сохранять существующую ролевую семантику до отдельного решения.
- Изменение статусов допускается только через отдельные HTTP-команды, а не `PATCH /orders/{id}`.

### 2.3. Переходы стадий

Только роль `admin`:
- Заказ: `under_review → in_progress` при `manager_review`, одновременно статус работы = `waiting_arrival`.
- Заказ: `under_review → completed` при `manager_review` **только с причиной отказа**, рабочий статус = `refused`.
- Заказ: `in_progress → completed`: из `execution` без причины → `owner_visit`; при непустой причине из `waiting_arrival`, `intake`, `owner_approval`, `execution` → `refused`; штатное завершение и отказ различать.
- Работа: `waiting_manager_review → manager_review`, `waiting_arrival → intake`, `intake → owner_approval`, `owner_approval → waiting_payment`, `waiting_payment → execution`; последний переход только при оплате `paid`.
- Оплата: изменение `unpaid/paid` только admin при `in_progress + waiting_payment`. Это **статус оплаты**, не интеграция с банком/кассой. Не добавлять финансовые проводки, которых не было в Django.
- Отказ освобождает время записи, но оставляет документ для истории.
- Правила переходов из регистров являются необходимым условием, но не заменяют проверки контекста выше.

### 2.4. Фильтры и права

Ключи: `search`, `order_number`, `vin`, `plate_number`, `brand`, `model`, `work_type`, `status`, `work_status`, `date_range`.
- Роль `user`: разрешены `search`, `order_number`. Видит только свои заказы, телефон клиента в JSON скрыт.
- Роли `mechanic` и `admin`: все ключи. В **текущем Django** механики видят все заказы, хотя доступ к автомобилям у них ограничен назначениями; при переносе нужно явно проверить согласованность правил до публичного включения.
- Механик не получает `price` и `works[].price`. Фильтры и ответы проверять в 1С и повторно ограничивать в Django.

## 3. HTTP API: добавить вручную в существующий ServiceCarAPI

Корень сохраняется: `/ServiceCar/hs/api`. Вся номенклатура — в одном сервисе только если 1С HTTP-сервис не допускает разделения публикаций; BSL лучше разделить на общие модули `ЗаказыAPIСервер`, `РасписаниеЗаказовСервер`, `МаршрутЗаказовСервер`, чтобы не раздувать текущий `ServiceCarAPI` с пользователями/MAX/авто.

| Шаблон | Методы |
|---|---|
| `/order-work-types` | GET |
| `/order-statuses` | GET |
| `/order-work-statuses` | GET |
| `/order-payment-statuses` | GET |
| `/order-schedule` | GET |
| `/order-availability` | GET (?date=YYYY-MM-DD) |
| `/orders` | GET, POST |
| `/orders/{id}` | GET, PATCH; DELETE не реализовывать до решения о допустимости удаления |
| `/orders/{id}/permissions` | GET |
| `/orders/{id}/transition-status` | POST |
| `/orders/{id}/transition-work-status` | POST |
| `/orders/{id}/payment-status` | POST |
| `/orders/filter-permissions` | GET |
| `/orders/by-car/{id}` | GET |
| `/orders/car/{id}/exists` | GET |

Внутренний контекст инициатора для всех операций: `actorId` (UUID пользователя 1С) и `actorRole` (`user` / `mechanic` / `admin`). **Важно:** эти поля передаёт только Django из проверенного JWT, НЕ клиент браузера; 1С по `actorId` перепроверяет активность пользователя, его роль в `РолиПользователей`, владение заказом/машиной и право на действие. Публикация HTTP API должна быть защищена сетевыми правилами и не принимать прямые обращения из интернета, даже если текущий внутренний канал работает без Basic Auth. Нельзя доверять произвольному `actorRole` без проверки регистра ролей в 1С.

Формат ошибок: JSON `{ "code": "invalid_transition", "message": "..." }`, корректные статусы 400/403/404/409/500. Для GET списков всегда JSON-массив. Для `GET /orders` — массив, пагинация остается во внешнем Django API.

```json
{

  "orderNumber": "000000001",
  "car": "uuid-car-1c",
  "carName": "Toyota Camry",
  "ownerPhone": "79990000000",
  "carYear": 2022,
  "carVin": "",
  "carPlateNumber": "",
  "works": [{"id": "uuid-row", "workTypeId": null, "name": "Диагностика", "price": "0.00"}],
  "mechanics": [],
  "status": {"id": "uuid-status", "code": "under_review", "name": "На рассмотрении", "requiresPayment": false},
  "workStatus": {"id": "uuid-work-status", "code": "waiting_manager_review", "name": "Ожидание проверки менеджером"},
  "paymentStatus": {"id": "uuid-payment-status", "code": "unpaid", "name": "Не оплачено"},
  "permissions": {
    "canTransitionStatus": false, "canTransitionWorkStatus": false,
    "canEditWorks": true, "canEditPrice": false, "canEditAppointment": true,

    "canChangePaymentStatus": false

  "description": "",
  "refusalReason": "",
  "price": "0.00",
  "createdAt": "2026-10-21T15:00:00+07:00"

```

UUID в JSON выше — **обозначение типа**, не реальные значения: при реализации должен быть действительный UUID. Числовые legacy ID вида работ/статусов после полного перехода заменятся на UUID 1С — Angular надо проверить и адаптировать перед cutover. Значения `appointmentAt` и `createdAt` должны иметь однозначную временную зону; JSON ISO-8601 с offset, никаких неявных локальных дат сервера. Текущая временная зона Django — `Asia/Krasnoyarsk`: подтвердить совпадение с зоной 1С при тестах.

### 3.2. Запросы создания/обновления

```json
{
  "car": "uuid-car-1c",
  "appointmentAt": "2026-10-22T09:00:00+07:00",
  "description": "Диагностика",
  "works": [{"workTypeId": null, "name": "Диагностика", "price": "0.00"}],
  "mechanics": []
}
```

Альтернатива начального создания — `workTypes: ["Диагностика"]` вместо `works`, тогда каждая строка получает цену 0. Внешний Django не передаёт цену от клиента как доверенную; изменение цен разрешается только admin в указанной фазе, иначе запрет. Пустое значение `appointmentAt` согласовать с текущим валидатором: при создании фронт обычно требует конкретную запись.

### 3.3. Расписание и доступность (как существующий API)

`GET /order-schedule` возвращает `{settings:{appointmentDuration,slotInterval}, weekdays:[{weekday,weekdayName,is_working,startTime,endTime}],blocks:[{date,startTime,endTime}]}`.
`GET /order-availability?date=YYYY-MM-DD` возвращает `{date,dayType,workingHours,appointmentDuration,slotInterval,availableSlots,busySlots,blockedSlots}`. Названия `dayType` — `working` и `nonWorking`; свободные слоты — строки `HH:MM`, интервалы `{from,to}`.

## 4. Порядок внедрения и критерии готовности

1. Через Конфигуратор **в тестовой копии ИБ** создать перечисленные справочники, документ, регистры, табличные части и включение в подсистему. Проверить структуру, `F7`, создать тестовую строку заказа.
2. Написать BSL в модулях: проверка записываемого документа, валидация прав, заполнение снимков, уникальность работ и специалистов, расчёт суммы, блокировка и резервирование дат, переходы статусов и HTTP обработчики. Сначала тестировать напрямую в 1С; затем HTTP.
