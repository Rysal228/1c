# Перенос заказов в 1С: ручное создание через Конфигуратор

> Актуализировано после выгрузки `main` 21.10.2026 и уточнений пользователя. **Не загружать XML/CF в 1С.** Все метаданные пользователь создаёт вручную, затем выгружает из Конфигуратора в GitHub. Этот документ — инструкция/контракт, а не готовая конфигурация и не подтверждение успешного обновления ИБ.

## Текущий фактический состав конфигурации (из main)

- `Справочники.ВидыРабот`: создан, стандартное Наименование длиной 100.
- `Справочники.СтатусыЗаказов`: создан; `КодСтатуса` Строка(50), `Начальный` Булево, `ТребуетОплаты` Булево.
- `Справочники.СтатусыРабот`, `СтатусыОплаты`: созданы, у обоих `КодСтатуса` Строка(50).
- `Документы.ЗаказыНаОбслуживание` (**именно это имя, НЕ ЗаказыНаРемонт**): создан, большинство реквизитов готовы, обе табличные части **пока без полей**, форма и модуль объекта в выгрузке отсутствуют.
- Регистры сведений `НастройкиЗаписи`, `НедельныйГрафик`, `БлокировкиЗаписи`, `ЗанятыеИнтервалы`: созданы; независимые и непериодические.
- Подсистема `Автосервис`: содержит все указанные объекты.
- В `HTTPServices.ServiceCarAPI` **пока нет** маршрутов заказов. Не переписывать существующие маршруты пользователей/MAX/авто.
- По выгрузке невозможно установить, были ли заполнены справочники/регистры пользовательскими данными и выполнено ли `F7`.

## Три обязательных бизнес-правила

1. **Работы необязательны:** документ может иметь 0 строк в `Работы` и создаваться/редактироваться без вида работы. Удалить обязательность `works`, `workTypes` из нового Django API; пустой `works: []` допустим.
2. **Никаких произвольных работ:** каждая имеющаяся строка `Работы` содержит **обязательную** ссылку `ВидРаботы` на существующий элемент `Справочники.ВидыРабот`. Нельзя посылать имя свободным текстом или создавать новый вид из формы заказа; название отдаётся из справочника. Пустая ссылка, несуществующий или помеченный на удаление вид запрещены. При повторном выборе одного вида в одном заказе — ошибка, если отдельно не согласовано иное.
3. **Свободные статусы:** текущие `СтатусЗаказа`, `СтатусРабот` — независимые поля. Авторизованный менеджер (`actorRole=admin`) может устанавливать **любой существующий статус соответствующего справочника из любого текущего статуса**. Нет обязательной цепочки, таблиц/регистров переходов, автоматического выставления одного статуса при смене другого или зависимости работы `execution` от `paid`. Существующий `Перечисления.РолиПользователей.Менеджер` соответствует API-роли `admin`. Роли, проверка владельца и актуальность выбранного значения — отдельные необходимые ограничения. `СтатусОплаты` также сохраняется как независимый статус, меняется менеджером. `ТребуетОплаты` в `СтатусыЗаказов` оставить для отображения/возможных будущих сценариев, но не использовать как скрытый запрет переходов.

Ранее планировавшиеся **регистры `ПереходыСтатусовЗаказов` и `ПереходыСтатусовРабот` НЕ создавать**. **Регистр `ДоступКФильтрамЗаказов` создать**, поскольку сейчас администратор может настраивать доступность фильтров в Django Admin и при полном переносе это поведение должно сохраниться в 1С.

## 1. Доделать через Конфигуратор

### 1.1. Документ `ЗаказыНаОбслуживание` → Табличные части

**Работы** (табличная часть уже существует, открыть её → Реквизиты → Добавить):

| Имя | Тип | Обязательность / смысл |
|---|---|---|
| `ВидРаботы` | `СправочникСсылка.ВидыРабот` | **Обязателен только для существующей строки**; проверять активную ссылку |
| `Цена` | Число(12,2), неотрицательное | Цена строки, изначально 0 |
| `ИдентификаторСтроки` | Строка(36) | Стабильный UUID строки для внешнего `works[].id` |

**Не добавлять свободный `Название`/текстовый `ТипРабот`**: имя = `ВидРаботы.Наименование`. Табличная часть **целиком необязательна**, её стандартная проверка заполнения — `Не проверять`. Если нет работ, сумма заказа равна 0. В API `works` всегда массив, в том числе пустой; поле `workTypes` как массив произвольных названий удалить при cutover (не раньше).

**Специалисты** (табличная часть существует, колонок ещё нет):
- `Специалист`: `СправочникСсылка.ПользователиПриложения`. Для каждой строки обязательно; весь список может быть пустым. Дубли запрещать. В 1С проверять `Активен` и наличие роли `Перечисления.РолиПользователей.Специалист` через регистр `РолиПользователей`.

### 1.2. Объектные реквизиты

У `ЗаказыНаОбслуживание` уже есть `Клиент`, `Автомобиль`, `СтатусЗаказа`, `СтатусРабот`, `СтатусОплаты`, `ДатаЗаписи`, `Описание`, `ПричинаОтказа`, `ТелефонКлиентаСнимок`, `ФиоКлиентаСнимок`, `МаркаСнимок`, `МодельСнимок`, `МаркаАвтомобиля`, `МодельАвтомобиля`, `ГодВыпускаСнимок`, `VINСнимок`, `ГосНомерСнимок`.

- Рекомендация: увеличить `ФиоКлиентаСнимок` со 150 до 450 символов (согласовать с реальной длиной ФИО).
- Ссылки клиента/авто/всех трёх статусов обязательны для записи на уровне BSL. `ДатаЗаписи` — дата+время, валидировать при заполнении. Снимки формировать при создании из справочников; не принимать произвольные значения из клиентского JSON.
- `Номер` и `Дата` — **стандартные** реквизиты документа. Уже установлена уникальная сквозная автонумерация длины 9; `orderNumber` берётся от номера 1С, `id` — собственный UUID ссылки.
- В выгрузке `Posting=Allow` («Проведение разрешено»), но `RegisterRecords` пусто и движения не реализованы. Пока не планируются движения через проведение — рекомендуем **запретить проведение**, чтобы не создавать ложную операцию; бронирование делать явной транзакцией в BSL. Если решено резервировать через проведение документа, потребуется другая модель связанных регистров и событий.
- Нужны `ФормаДокумента`, при необходимости `ФормаСписка`; из дерева выгрузки формы сейчас отсутствуют.

### 1.3. Справочники и регистры

- `ВидыРабот`: наполняет менеджер в 1С; выбрать можно только существующий элемент, без создания нового пользователем в форме заказа.
- `СтатусыЗаказов`, `СтатусыРабот`, `СтатусыОплаты`: уникальный `КодСтатуса` без пробелов в начале/конце; проверять уникальность при сохранении. Обычный `Код` платформы — не `КодСтатуса` API.
- Заполнить данные `СтатусыЗаказов`: `under_review` (начальный), `in_progress`, `completed`; `СтатусыРабот`: `waiting_manager_review`, `manager_review`, `waiting_arrival`, `intake`, `owner_approval`, `waiting_payment`, `execution`, `owner_visit`, `refused`; `СтатусыОплаты`: `unpaid`, `paid`. Все значения редактируемые по имени, а выбор следующего статуса **свободный**, без матрицы переходов.
- `НастройкиЗаписи`: одна запись `Ключ=main`, `ДлительностьМинут=60`, `ИнтервалМинут=30`. Проверять оба значения 5..1440 и интервал не больше длительности.
- `НедельныйГрафик`: 0=пн…6=вс; 0..4 рабочие 540..1200 (09:00..20:00), 5..6 выходные.
- `БлокировкиЗаписи`, `ЗанятыеИнтервалы`: минуты от начала суток, интервалы в рамках суток; даты с составом **Дата**, без времени. Сохранить связи через `ДокументСсылка.ЗаказыНаОбслуживание`.
- **Новый регистр `ДоступКФильтрамЗаказов`** (независимый, непериодический): измерения `Роль` — `ПеречислениеСсылка.РолиПользователей`, `КлючФильтра` — Строка(30); ресурс `Разрешен` — Булево. Ключи: `search`, `order_number`, `vin`, `plate_number`, `brand`, `model`, `work_type`, `status`, `work_status`, `date_range`. Начальные права как в Django: для `Пользователь` разрешены `search` и `order_number`, для `Специалист` и `Менеджер` все фильтры. В 1С предусмотреть настройку записей регистра менеджером.
- Для этих независимых регистров ещё нужны BSL-проверки диапазонов/пересечений и защита одновременной записи.

### 1.4. Модули 1С, которых пока нет в выгрузке

**Модуль объекта документа**: проверка клиента и права владения активным автомобилем (`Автомобиль.ВладелецАвтомобиля = Клиент`, `ВАрхиве = Ложь` при создании), заполнение снимков; проверка работ/специалистов, нормализация строкового UUID и вычисление суммы как сумма `Работы.Цена`; запрет смены авто после создания; статус из своего справочника без матрицы переходов. Проверку нужно ставить также на сервере 1С при записи не через браузер.

**Общий модуль серверной логики заказов** (рекомендуемые имена `ЗаказыСервер`, `ЗаписьНаОбслуживаниеСервер`): поиск, сериализация, назначение, права, проверка слотов и целостный перенос времени с транзакцией и блокировкой даты. Два одновременных HTTP-запроса на один слот не могут записать два заказа.

**Обработчики HTTP**: см. ниже. Публикация не должна быть доступна извне: инициатор, передаваемый внутренним Django, должен проверяться в 1С по существующему справочнику/регистру ролей. Не доверять браузерным `actorId` / `actorRole`.

## 2. Контракт HTTP для Django

Добавлять шаблоны URL **вручную** в существующий `HTTPServices.ServiceCarAPI` (не заменять его код). Корень: `/ServiceCar/hs/api`.

| Внутренний URL | Методы |
|---|---|
| `/order-work-types` | GET |
| `/order-statuses` | GET |
| `/order-work-statuses` | GET |
| `/order-payment-statuses` | GET |
| `/order-schedule` | GET |
| `/order-availability?date=YYYY-MM-DD` | GET |
| `/orders` | GET, POST |
| `/orders/{id}` | GET, PATCH |
| `/orders/{id}/permissions` | GET |
| `/orders/{id}/transition-status` | POST (разрешить любой существующий статус; имя HTTP оставлено ради внешней совместимости) |
| `/orders/{id}/transition-work-status` | POST (разрешить любой существующий статус) |
| `/orders/{id}/payment-status` | POST |
| `/order-filter-permissions` | GET |
| `/orders/by-car/{id}` | GET |
| `/orders/car/{id}/exists` | GET |

**Контекст:** `actorId` (UUID пользователя) и `actorRole` (`user`, `mechanic`, `admin`) всегда серверное значение от Django, передаётся через параметры запроса. В 1С обязательна проверка действительности UUID пользователя, активности, его роли через регистр `РолиПользователей`, владельца заказа и запрет действий не той роли. `admin` → перечисление `РолиПользователей.Менеджер`.

**Параметры создания/редактирования:**
```json
{
  "car": "00000000-0000-0000-0000-000000000001",
  "appointmentAt": "2026-10-22T09:00:00+07:00",
  "description": "Диагностика",
  "works": [
    {"workTypeId": "00000000-0000-0000-0000-000000000002", "price": "0.00"}
  ]
}
```
Здесь UUID — только синтаксические примеры, не реальные ссылки. `works` можно опустить или передать `[]`; тогда заказ без работ. Если `works` задан непустой, `workTypeId` в каждой строке — **обязательная ссылка**; никаких `name` и `workTypes: ["текст"]`. Бэкенд не должен доверять присланному `price` от `user`: цена редактируется менеджером. `works[].name` в ответе — название из справочника; `works[].id` — `ИдентификаторСтроки`. Значения перечисленных статусов в API — `{id,code,name}` с UUID 1С; Angular потребуется адаптировать с Django-числовых PK на UUID.

**Ответы:** внешний контракт сохранить максимально близким к `/api/v1/orders/` текущего Django: `id`, `orderNumber`, `car`, `carName`, `ownerPhone`, `carYear`, `carVin`, `carPlateNumber`, `works`, `mechanics`, `status`, `workStatus`, `paymentStatus`, `permissions`, `appointmentAt`, `description`, `refusalReason`, `price`, `createdAt`; `price` вычисляется 1С из строк работ. Не показывать клиенту чужие заказы и телефон, не показывать специалисту цены — проверки на стороне 1С и Django.

**Свободные переходы:** методы `transition-status` и `transition-work-status` остаются в API, но запрос означает «установить указанное значение» без цепочек и скрытых связанных переходов. Значение `statusId` должно ссылаться на существующий активный элемент соответствующего справочника. Только `admin` может менять статусы через эти методы, как раньше. Специалист не меняет их через текущий API.

**Запись на время:** перед фактическим сохранением повторная проверка доступности в одной транзакции с управляемой блокировкой даты регистра `ЗанятыеИнтервалы`. Список `availableSlots` — подсказка пользователю, не гарантия бронирования. Правила `09:00–20:00`, шаг 30, длительность 60, суб/вс выходные по умолчанию; глобальная вместимость = один заказ на интервал. При изменении графика определиться с политикой обработки занятых слотов. **Изменение статуса само по себе не освобождает слот**: для отмены/освобождения нужна отдельно согласованная команда либо явное изменение даты записи. Это избегает скрытой связки статусов.
