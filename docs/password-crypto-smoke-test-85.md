# Безопасная проверка платформенного хеширования в 1С 8.5.1.1522

**Предварительные условия:** в информационной базе выбран PBKDF2 SHA-256;
регистр сведений `ПаролиПользователейПриложения` уже создан и обновлена конфигурация БД;
функции `ВычислитьХешПароляПриложения`, `УстановитьПарольПриложения`,
`ПроверитьПарольПриложения` добавлены в модуль HTTP-сервиса и
прошли проверку синтаксиса.

Пока **не** выполнять установку пароля ни для одного реального пользователя.
В текущей публикации API нет защищённых обработчиков для парольного входа.
Не добавлять парольный POST в `ServiceCarAPI` с доступом без технической
авторизации.

## Тест 1. Криптография без доступа к БД — запуск строго на сервере

**Исправление инструкции:** не вставлять тест в `МодульУправляемогоПриложения`:
этот модуль проверяется в контексте тонкого клиента, в котором
`ВычислитьСохраняемоеЗначениеПароляПользователя` и
`ПроверитьСоответствиеПароляПользователяСохраняемомуЗначению`
недоступны. Ошибка `Проверка: Тонкий клиент` не означает, что методы
отсутствуют в платформе или не работают в серверном HTTP-модуле.

Создать **временную внешнюю обработку с управляемой формой** в
Конфигураторе. В форме создать команду `ПроверитьПароли`, а в **модуль
формы**, а не в модуль управляемого приложения, вставить:

```bsl
&НаСервереБезКонтекста
Функция СамотестПаролейНаСервере()
    ТестовыйПароль = "OneC-Smoke-Test-Only!2026";
    Значение = ВычислитьСохраняемоеЗначениеПароляПользователя(
        ТестовыйПароль);

    Если НЕ ПроверитьСоответствиеПароляПользователяСохраняемомуЗначению(
        ТестовыйПароль, Значение) Тогда
        ВызватьИсключение "Правильный тестовый пароль отклонен.";
    КонецЕсли;

    Если ПроверитьСоответствиеПароляПользователяСохраняемомуЗначению(
        "Obviously-Wrong-Smoke-Test!2026", Значение) Тогда
        ВызватьИсключение "Неправильный тестовый пароль принят.";
    КонецЕсли;

    // Тип возвращаемого значения нужно проверить ДО реальной записи
    // в строковый ресурс регистра. Само значение не показываем.
    Возврат "PASS. Тип значения: " + Строка(ТипЗнч(Значение));
КонецФункции

&НаКлиенте
Процедура ПроверитьПароли(Команда)
    Сообщить(СамотестПаролейНаСервере());
КонецПроцедуры
```

Связать команду `ПроверитьПароли` с одноимённым обработчиком, открыть
внешнюю обработку в режиме 1С:Предприятие и нажать команду.

Код выполняет вычисление только с фиксированным искусственным паролем,
**не использует HTTP**, не обращается ни к регистру, ни к справочнику,
не пишет данные и не возвращает хеш клиенту.

Ожидаем `PASS. Тип значения: Строка` (если платформа вернёт иной тип,
это важный сигнал: надо адаптировать тип ресурса/преобразование, **не
записывая пароль**).

Этот тест доказывает совместимость парных методов, но сам по себе не
доказывает, что выбран конкретный алгоритм. Алгоритм проверить в
параметрах ИБ и через серверный `ПолучитьТипАлгоритмаХешированияПаролейПользователя()`
по Синтакс-помощнику текущей версии.

Если серверный тест не компилируется, сообщить точную ошибку,
не подменять встроенные функции собственным SHA256 и не задавать
пароли реальным пользователям.

## Тест 2. Проверка метаданных регистра

В Конфигураторе убедиться:
- `ПаролиПользователейПриложения` — непериодический независимый регистр.
- Измерение `Пользователь`: ссылка справочника `ПользователиПриложения`,
  непустая/одна запись на пользователя.
- Ресурс `СохраняемоеЗначение`: `Строка(2048)`, режим пароля в UI,
  без полнотекстового поиска и истории изменений.
- Запрет чтения и изменения регистра для обычных ролей и внешних
  пользователей, не только скрытие списка. Права должен иметь лишь
  специально выделенный серверный компонент/роль.

## Проверка будущей записи хеша

Позднее (после разделения сервиса и настройки защищённого доступа)
испытать процедуру `УстановитьПарольПриложения` **только на отдельном
тестовом пользователе**, затем правильный/неправильный пароль через
`ПроверитьПарольПриложения`, смену пароля, отсутствие записей для MAX-only
и отказ для неактивного/помеченного на удаление пользователя.

Не повторять запись хеша отладки на реальных 3 пользователях.
Не публиковать внутренние функции в действующем `ServiceCarAPI`;
требуется отдельный аутентифицированный TLS HTTP-сервис.

После проверок следующий PR создаст:
- внутренний HTTP verify endpoint, который **не возвращает хеши**;
- процедуру первичной установки новых паролей с подтверждением личности;
- ограничение частоты/блокировку попыток;
- переход логина только после end-to-end теста.
Регистрация и MAX не затронуты данным PR.
